# RAG 检索评测报告

评测日期：2026-08-30  
评测对象：Go/GSE/PostgreSQL/pgvector/Qwen RAG 检索链路

## 1. 最终结论

本轮补充实验修正了旧基线的两个缺陷：旧文档几乎一篇只产生一个 Chunk，无法评价切片；旧查询与文档由同一模板生成，明显偏向词面匹配。最终实验改用 2,120～3,074 字符长文档、独立人工问句和按业务主题隔离的 dev/test 集。

结论以 **24 条未参与选型的 test 查询** 为准：

1. 当前线上 `500/100` 切片并非最优。dev 集选出的候选 `1200/200`，在离线 Hybrid 上把 test Hit@5 从 **70.83% 提升到 95.83%**、Precision@5 从 **16.67% 提升到 27.50%**、MRR 从 **0.3812 提升到 0.7410**。
2. overlap 有实际价值。`500/0` 将 15 条边界答案切断，`500/100` 不再破坏这些答案；但 overlap 会制造重复相关 Chunk，不能脱离 size 单独判断。
3. 独立自然问句下，向量召回比当前关键词召回更稳。真实生产 `noise120` 上，Vector、`pg_fts`、Hybrid 的 test Hit@5 分别为 **75.00%、41.67%、62.50%**。当前等权 RRF 会被较弱的关键词分支拖累，不能再宣称“混合检索一定优于单路”。
4. 真正 BM25 仍值得实现，但旧实验中“BM25 明显占优”的结论不成立。使用候选切片的离线 test 上，BM25、Vector、Hybrid 的 Hit@5 分别为 **87.50%、100%、95.83%**；Hybrid 的 MRR 最高，为 **0.7410**。
5. 文档生命周期过滤是高优先级改进。移除废止版本后，离线 Hybrid test Hit@5 从 95.83% 升至 100%，MRR 从 0.7410 升至 0.8958；真实当前链路也表现出相同方向。
6. 发现并修复了带 `kb_id` 过滤的 HNSW 召回缺失：多个知识库共享全局索引时，默认 ANN 可能先取到其他知识库的近邻，再被过滤掉，导致结果不足甚至为空。现在向量查询在事务内启用 pgvector iterative scan 并提高搜索范围。
7. **本轮没有把生产切片改成 `1200/200`，也没有把生产关键词实现改成 BM25。** 前者是待 A/B 的候选配置，后者是待落地验证的候选算法；真实生产评测仍使用当前 `500/100 + ts_rank_cd + Vector + RRF`。

## 2. 数据集与独立性

### 2.1 语料

所有规则和数值均为确定性生成的虚构材料，不代表真实业务政策。

| 子集 | 文档数 | 构成 | 用途 |
|---|---:|---|---|
| `core` | 48 | 16 现行规则 + 16 高相似废止版 + 16 同领域干扰文档 | 切片、召回算法比较 |
| `active120` | 152 | 16 现行规则 + 16 同领域干扰 + 120 背景文档 | 生命周期过滤上界 |
| `noise120` | 168 | `core` + 120 背景文档 | 噪声和真实链路验证 |

文档长度最短 2,120、最长 3,074、平均 2,967 字符。当前 `500/100` 在 `core` 上产生 384 个 Chunk，平均每篇 8 个；实验不再是“文档≈Chunk”的伪切片测试。每个业务主题还包含一条刻意跨越 500 字符边界的答案，用于检验 overlap。

### 2.2 查询与数据隔离

- 共 16 个业务主题、64 条查询，每个主题 4 条。
- 查询由独立 `QUERY_BANK` 人工编写，不从文档模板抽取或拼接。
- 覆盖改写、隐式表达、精确代码、场景化、口语化和边界答案六类。
- 按主题而不是按问句切分：10 个主题、40 条查询用于 dev 选参数；另外 6 个从未参与选型的主题、24 条查询只用于 test 报告结果。

这避免了同一主题的近似问句同时进入训练式选参集和测试集。它仍是内部合成集，而非真实用户日志；因此可以支撑工程选型，却不能冒充最终线上效果。

## 3. 评测方法

评测分两层：

| 层次 | 内容 | 作用 |
|---|---|---|
| 离线算法层 | 真实 Qwen 2048 维 Embedding、生产 GSE 分词、Python Okapi BM25/Vector/RRF、可变切片 | 快速做消融和只用 dev 选参 |
| 真实生产层 | HTTP API → Go → PostgreSQL GIN/`ts_rank_cd` → pgvector HNSW → SQL RRF | 验证当前代码、入库、索引和查询行为 |

离线 BM25 是 Okapi BM25（`k1=1.5, b=0.75`）；生产模式名统一写为 `pg_fts`，因为它实际是 PostgreSQL `ts_rank_cd`，不能把两者混称。

相关性按 Chunk 判断：Chunk 必须来自目标现行文档，并完整包含人工标注的答案片段。废止版即使包含相似文字，也不算正确。

## 4. 指标含义

- **Hit@K**：每条查询的前 K 个结果中只要有一个正确 Chunk 即记 1，再对查询求平均。单答案检索中它等价于常说的 query-level Recall@K；报告使用 Hit@K 避免与多相关项召回混淆。
- **Precision@K**：前 K 个结果中正确 Chunk 的比例。它衡量送给 LLM 的上下文有多“干净”。因为 overlap 可能让一个答案对应多个正确 Chunk，本轮该指标终于具有区分度。
- **Chunk Recall@K**：检出的正确 Chunk 数 / 全部正确 Chunk 数，用于观察 overlap 产生多个相关片段后的覆盖率。
- **MRR**：第一个正确结果排名倒数的均值。正确答案排第 1 得 1，排第 2 得 0.5，未命中得 0；越高表示正确内容越靠前。
- **NDCG@K**：考虑排名位置的归一化累计增益；正确结果越靠前、多个正确 Chunk 覆盖越充分，分数越高。
- **retired-before-gold**：废止版出现在首个正确现行结果之前的查询比例，越低越好。
- **context chars**：Top-K 返回文本总字符数，近似反映后续 LLM 的上下文成本。
- **P50/P95**：50%/95% 请求不超过的检索延迟。离线 Python 耗时只用于相同实现内横向比较，生产 HTTP 延迟才代表当前服务。

## 5. 实验结果

除特别说明外，下表均为 test 集、Top-K=5。

### 5.1 切片规模与 overlap

在 `core` 上使用离线 Hybrid：

| 配置 | Chunk 数 | Hit@5 | Precision@5 | MRR | 平均上下文字符 |
|---|---:|---:|---:|---:|---:|
| fixed 300/0 | 512 | 0.7500 | 0.1500 | 0.4646 | 1,266 |
| fixed 300/60 | 656 | 0.7083 | 0.1417 | 0.3347 | 1,255 |
| fixed 500/0 | 304 | 0.5833 | 0.1167 | 0.3750 | 1,825 |
| **当前 fixed 500/100** | 384 | 0.7083 | 0.1667 | 0.3812 | 2,055 |
| fixed 800/0 | 208 | 0.9583 | 0.1917 | 0.6785 | 3,525 |
| fixed 800/160 | 224 | 0.9167 | 0.2833 | 0.6535 | 3,650 |
| fixed 1200/0 | 128 | 0.9167 | 0.1833 | 0.6431 | 4,575 |
| **dev 选中 fixed 1200/200** | 160 | **0.9583** | 0.2750 | **0.7410** | 4,730 |
| heading 500/100 | 528 | 0.7083 | 0.1417 | 0.4681 | 1,037 |

`1200/200` 的排序最好，但每次 Top-5 上下文约比当前配置多 2,675 字符。`800/0` 达到相同 Hit@5，成本更低，但 MRR 和 Precision 较弱。因此建议把 `1200/200` 作为质量优先候选、`800/0` 作为成本均衡候选，再做端到端答案评测，不直接修改默认值。

`500/0` 的低分不是偶然：它把 16 个刻意构造的边界答案中的 15 个切成两半，使任何 Chunk 都不再包含完整 gold span；`500/100` 修复了这个结构性问题。

### 5.2 当前配置下的召回器

离线 `core + 500/100`：

| 模式 | Hit@5 | Precision@5 | MRR |
|---|---:|---:|---:|
| BM25 | 0.6250 | 0.1583 | 0.4375 |
| Vector | **0.7500** | **0.1750** | 0.3604 |
| Hybrid | 0.7083 | 0.1667 | 0.3812 |

独立问句减少了文档原词复现，旧短基线中关键词近乎满分的现象消失。这正说明原测试集存在模板同源偏差。

### 5.3 候选切片下的 BM25、Vector 与 Hybrid

离线 `1200/200`：

| 子集 | 模式 | Hit@5 | Precision@5 | MRR |
|---|---|---:|---:|---:|
| core | BM25 | 0.8750 | 0.2500 | 0.6278 |
| core | Vector | **1.0000** | **0.2917** | 0.6562 |
| core | Hybrid | 0.9583 | 0.2750 | **0.7410** |
| noise120 | BM25 | 0.8333 | 0.2417 | 0.6403 |
| noise120 | Vector | **1.0000** | **0.2917** | 0.6562 |
| noise120 | Hybrid | 0.9583 | 0.2750 | **0.7410** |

120 篇普通背景文档几乎没有影响向量与 Hybrid，但 BM25 Hit@5 小幅下降。选型结论应表述为：**向量负责语义召回，真正 BM25 对精确词项有补充价值，RRF 在本集上改善首个正确结果排序；当前 `ts_rank_cd` 还没有达到离线 BM25 的效果。**

### 5.4 Top-K

离线 `noise120 + 1200/200 + Hybrid`：

| K | Hit@K | Precision@K | MRR | 平均上下文字符 |
|---:|---:|---:|---:|---:|
| 1 | 0.5833 | 0.5833 | 0.5833 | 866 |
| 3 | 0.8750 | 0.3611 | 0.7222 | 2,768 |
| 5 | 0.9583 | 0.2750 | 0.7410 | 4,731 |
| 8 | 1.0000 | 0.1823 | 0.7479 | 7,568 |
| 10 | 1.0000 | 0.1458 | 0.7479 | 9,414 |

K=8 可补齐最后 4.17% 查询，但相对 K=5 增加约 60% 上下文，MRR 只增加 0.0069。默认 5 仍是合理折中；需要高召回的离线分析可使用 8。

### 5.5 生命周期过滤

离线 `noise120 + 1200/200` 去掉废止文档后：

| 模式 | Hit@5 | Precision@5 | MRR |
|---|---:|---:|---:|
| BM25 | 0.9167 | 0.2694 | 0.7826 |
| Vector | 1.0000 | 0.2917 | 0.8681 |
| Hybrid | 1.0000 | 0.2833 | **0.8958** |

这比让 reranker 猜测哪份政策有效更可靠。生产设计应给文档增加 `effective_status/effective_from/effective_to` 等元数据，在关键词和向量召回的 SQL 中先过滤，再进行 RRF 或 rerank。

## 6. 真实生产链路复验

真实链路保持当前 `500/100`，完成 Markdown 扫描、Asynq 摄取、Qwen Embedding、`halfvec(2048)` 入库、GIN/HNSW 查询和 RRF。实际 Chunk 数为：`core=384`、`active120=1200`、`noise120=1344`。

`noise120` 的 test 结果：

| 模式 | Hit@1 | Hit@3 | Hit@5 | Precision@5 | MRR | 废止版抢先率 |
|---|---:|---:|---:|---:|---:|---:|
| `pg_fts` | 0.1667 | 0.3333 | 0.4167 | 0.1000 | 0.2597 | 0.5000 |
| Vector | 0.1667 | **0.5833** | **0.7500** | **0.1750** | **0.3917** | 0.6667 |
| Hybrid/RRF | **0.2083** | 0.2500 | 0.6250 | 0.1500 | 0.3139 | 0.7917 |

`active120` 不含废止版本，Vector 的 Hit@5/MRR 从 0.7500/0.3917 改善为 0.7917/0.5174，Hybrid 从 0.6250/0.3139 改善为 0.7917/0.3917。真实链路再次验证了生命周期治理的方向。

当前 Hybrid 不如 Vector 的原因不是 RRF 公式失效，而是两个输入分支质量不对称：`pg_fts` 对自然改写召回较弱，等权融合会把它的错误高排名带入结果。合理顺序是先实现并评测真正 BM25，或用 dev 数据学习/网格选择分支权重，再决定线上默认模式。

生产全量 64 查询的缓存命中 P95 大致为：`core` 上 `pg_fts/vector/hybrid` 为 7.60/4.64/8.09 ms；`noise120` 为 18.91/8.07/21.70 ms。样本只有千级 Chunk，这些数字只能说明当前开发环境开销，不能外推到十万或百万规模。

## 7. HNSW 过滤问题与修复

评测同时创建了多个内容相近的知识库。`kb_chunks` 的 HNSW 是全局索引，而查询还有 `kb_id`、状态和 Embedding identity 过滤。默认近似搜索可能先从全局索引取得其他 KB 的近邻，随后 WHERE 过滤将其删除，最终目标 KB 返回不足 Top-K。

修复是在每次含向量的查询事务内设置：

```sql
SET LOCAL hnsw.iterative_scan = strict_order;
SET LOCAL hnsw.ef_search = 200;
SET LOCAL hnsw.max_scan_tuples = 100000;
SET LOCAL hnsw.scan_mem_multiplier = 4;
```

iterative scan 会在过滤后结果不足时继续扫描。设置只在只读查询事务内生效，不改变其他连接。修复后多个近重复 KB 均能稳定返回目标 Top-K；代价是过滤选择性很差时扫描和延迟增加。该修复属于主平台正确性修复，不只是评测脚本修改。

## 8. 本次改进与旧基线的关系

旧短基线保留在结果文件中供回溯，但不再用于最终选型。被撤回的结论包括：

- “500 字符切片最稳”：旧文档太短，实际没有充分切片。
- “overlap 没有收益”：旧数据没有构造跨边界答案。
- “关键词/Hybrid 几乎满召回”：查询与文档同模板，词面重合过高。
- “Top-K=3 已满召回”：在独立 test 中，候选配置 K=3 只有 87.50%，K=5 为 95.83%。

新实验也不是终点。它修复了切片有效性、查询同源和参数泄漏问题，但仍缺少：真实用户查询、多人盲标、无答案问题、多文档联合回答、最终 LLM 忠实度/正确率、reranker 对照以及大规模容量压测。

## 9. 最终工程建议

1. 保留 PostgreSQL + pgvector 架构；当前规模无需引入 Milvus。HNSW 过滤修复已解决本轮显式正确性问题。
2. 暂不直接改默认切片。用真实文档和答案级评测 A/B `500/100`、`800/0`、`1200/200`；质量优先先试 `1200/200`，成本优先先试 `800/0`。
3. 实现真正 BM25 生产候选后，与 Vector、加权 Hybrid 同数据复验；在此之前，默认 Hybrid 没有充分指标依据。
4. 优先补文档生效状态过滤，再考虑 reranker。reranker 解决相关性排序，不负责版本治理。
5. 保持 Top-K=5；需要极致召回的离线场景可调到 8，但应同时限制上下文或增加 rerank。
6. 下一轮至少加入 50～100 条匿名化真实问句、无答案样本和人工相关性等级，再测检索指标与答案正确率/忠实度。
